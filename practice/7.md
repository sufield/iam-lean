Just like with `#check "Hello World"`, we must distinguish between the **Command** (the `#check` instruction) and the **Expression** (the number `42`).

However, the `Expr` for `42` is more complex than a string because numbers in Lean are **overloaded** (they can be `Nat`, `Int`, `Float`, etc.).

### The Expression (`Expr`) Tree

When you type `42`, Lean defaults to `Nat` and uses the `OfNat` typeclass to "wrap" the raw literal. The tree looks like:

```text
               Expr.app (Application)
              /        \
          Expr.app      [Instance: instOfNatNat 42]  <-- How to make 42
         /        \
     Expr.app      Expr.lit (natVal 42)             <-- The raw number
    /        \
Expr.const    Expr.const `Nat                       <-- The target type
`OfNat.ofNat
```

### Why is it so complex?

1.  **Polymorphism:** Lean doesn't know if `42` is a `Nat` or an `Int` until it looks at the context.
2.  **`OfNat.ofNat`**: This is a special function that converts a raw "natural literal" into your desired type.
3.  **The Instance**: The third argument is a "proof" or "instruction" (the typeclass instance) telling Lean: *"Here is  how to treat the number 42 as a Nat."*

### The Command (`Syntax`)

The `#check` command itself is part of the **Syntax Tree**, not the logic tree:

```text
Syntax (node `Lean.Parser.Command.check)
├── Syntax (atom "#check")
└── Syntax (node `Lean.Parser.Term.num)  <-- The raw "42" you typed
```

### Pro Tip for the Infoview:

If you want to see this complexity yourself, try running this in Lean:

```lean
set_option pp.explicit true
#check 42
```

The Infoview will change from `42 : Nat` to something like:
`@OfNat.ofNat Nat 42 (instOfNatNat 42)`
This reveals the actual **`Expr`** nodes the Lean Kernel is processing!

---

@OfNat.ofNat Nat (nat_lit 42) (instOfNatNat (nat_lit 42)) : Nat

That output is the **exact textual representation** of the `Expr` tree we’ve been drawing.

Here is how that output maps to the internal nodes:

### 1. `@OfNat.ofNat` (`Expr.const`)

The `@` symbol tells Lean: "Show me every single argument in the tree, even the ones usually hidden." `OfNat.ofNat` is the fundamental constant function used to turn raw digits into a specific type.

### 2. `Nat` (Type Argument)

This is the first argument. It tells the function: "I want the result to be a `Nat`." If you had written `(42 : Int)`, this node would change to `Int`.

### 3. `(nat_lit 42)` (`Expr.lit`)

This is the raw value. In the Lean kernel, `nat_lit` is the most primitive form of a natural number. It is the actual data leaf of the tree.

### 4. `(instOfNatNat (nat_lit 42))` (The Instance)

This is the most "Lean-specific" part. It is an **automatically generated term** (a typeclass instance) that proves: *"I know how to convert the literal 42 into the type Nat."*

### The "Curried" Application Tree

In the AST, this is just four nested **`Expr.app`** nodes:

```text
(((OfNat.ofNat Nat) (nat_lit 42)) (instOfNatNat 42))
```

By seeing this, you now understand why Lean is so flexible. If you define a custom type (like `MyType`) and provide an `instance` for `OfNat MyType 42`, you can type `#check 42` and Lean will simply swap the `Nat` and `instOfNatNat` nodes for your custom ones. 

**The syntax (`42`) stays the same, but the AST (`Expr`) changes to match your logic.**
