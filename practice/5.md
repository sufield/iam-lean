This expression is more complex because `List` is **polymorphic** (it needs to know the type of its elements) and the list itself is a recursive structure.

### 1. The High-Level View

The function `List.reverse` has an implicit type argument `{α : Type}`. For `[1, 2, 3]`, Lean infers `α = Nat`.

```text
               Expr.app (Application)
              /        \
          Expr.app      [The List Structure] (see below)
         /        \
    Expr.const         Expr.const `Nat
    `List.reverse      (Implicit Type Argument)
```

---

### 2. The List Structure View

In Lean, `[1, 2, 3]` is sugar for `List.cons 1 (List.cons 2 (List.cons 3 List.nil))`. Each `cons` also takes the implicit type `Nat`. 

The "List Structure" node above is this nested tree:

```text
               Expr.app (cons)
              /        \
          Expr.app      [Next List Node: List.cons 2 ...]
         /        \
     Expr.app      Expr.lit (natVal 1)
    /        \
Expr.const    Expr.const `Nat
`List.cons
```

---

*   **Implicit Type Arguments:** Unlike `String.length`, `List.reverse` needs to know *what* it is reversing. In the AST, `Nat` is passed as a real argument before the list even arrives.
*   **Lists are Trees:** A list isn't a flat array in the AST; it is a linked structure of `Expr.app` nodes.
*   **Polymorphism in Infoview:** If you see an error like `List.reverse ?m.1`, it means the `Expr.const Nat` node is missing because Lean couldn't figure out what type of elements were in your list.
*   **Performance Insight:** When you write `[1, 2, 3]`, you are asking the **Elaborator** to construct a deep tree of applications. This is why very long literal lists can sometimes slow down compilation!
