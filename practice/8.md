Compared to the number `42`, the AST for `true` is much simpler because `true` is not overloaded—it is a specific value belonging to a specific type.

### 1. The Expression (`Expr`)

The word `true` in Lean 4 is a **constant** (specifically, a constructor of the `Bool` inductive type). Its internal name is `Bool.true`.

```text
Expr.const `Bool.true []
```

### 2. Why is this so simple?

*   **No Typeclasses:** Unlike `42` (which uses `OfNat`) or `+` (which uses `HAdd`), `true` is always a `Bool`. Lean doesn't need to look up a "how to handle this" instance.
*   **No Arguments:** `Bool.true` is a "nullary" constructor, meaning it doesn't take any arguments. It is a complete leaf node on its own.

### 3. Comparison of `Expr` Trees

| Code | AST Type | Internal Name | Why? |
| :--- | :--- | :--- | :--- |
| **`"Hello"`** | `Expr.lit` | `.strVal "Hello"` | It is a "raw" string literal. |
| **`42`** | `Expr.app` | `OfNat.ofNat ...` | It is a polymorphic number that needs a typeclass. |
| **`true`** | **`Expr.const`** | `Bool.true` | It is a fixed constructor of an inductive type. |

### 4. The Command (`Syntax`)

The `#check` command remains part of the outer **Syntax Tree**:

```text
Syntax (node `Lean.Parser.Command.check)
├── Syntax (atom "#check")
└── Syntax (ident `true)
```

**What happens in the Infoview:**

When you run `#check true`, Lean sees the constant `Bool.true`, looks up its definition in the environment, finds that it was defined as part of the `Bool` type, and prints:
`true : Bool`

*If you meant the proposition **`True`** (capital T), the AST is also an `Expr.const` pointing to `True`, but its type is `Prop` instead of `Bool`.*
